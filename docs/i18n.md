# Internationalization (i18n)

**Purpose:** Wording lives in JSON string catalogs — one per language, like Android `values/` + `values-he/`. Templates reference keys; `build.mjs` resolves them. You never edit user-facing text in the generated HTML.

## Catalog model

```
i18n/en/common.json     shared UI strings (nav, footer, a11y labels, badges)
i18n/en/<page>.json      per-page strings — the "strings.xml" for one page
i18n/he/common.json     Hebrew mirror of common
i18n/he/<page>.json      Hebrew mirror of the page
```

Languages: `en`, `he` (the `LANGS` array in `build.mjs`). Pages: `home`, `privacy`, `terms`, `guidelines`, `support`.

## How strings resolve

For each page + language, `build.mjs` merges two catalogs into one namespaced object:

```js
{ common: {…common.json}, home: {…home.json} }
```

`{{t:common.nav_privacy}}` and `{{t:home.hero_lead}}` are dotted lookups into that object. A missing key logs `! missing string: <path>` and renders empty — it does not fail the build, so **keep `en` and `he` catalogs in sync**.

### Per-page catalog shape

- `_meta`: `title`, `description` (→ `<head>`), `h1`, `updated` — `_meta` itself is never rendered directly; its fields flow in as `vars`.
- `intro`: raw HTML rendered before `{{sections}}` in the `legal` template (only `guidelines` defines it; privacy/terms omit it → empty).
- `sections[]`: `{ id?, heading?, body }` → `{{sections}}` emits `<section class="prose__block">`.
- `faq[]`: `{ id?, q, a }` → `{{faq}}` emits `<details class="faq">`.
- Plain keys (e.g. `home.hero_sub`, `support.sub`) → referenced individually via `{{t:…}}`.

`body`/`a`/`intro` values are **raw HTML** (`<p>`, `<ul>`, `<a href='terms.html'>`, `<div class='callout'>`) and are injected verbatim — author them as trusted content.

## Common tasks

**Change wording** → edit `i18n/en/<page>.json` and `i18n/he/<page>.json`, then `node build.mjs`.

**Add a page**
1. `i18n/en/<page>.json` + `i18n/he/<page>.json` (with `_meta`, plus `sections`/`faq` as the chosen template needs).
2. Reuse a body template (`legal`, `support`, `home`) or add `templates/pages/<shape>.html`.
3. Register it in the `PAGES` array in `build.mjs` (`i18n`, `tpl`, `out`, `url`).
4. `node build.mjs`.

**Add a language**
1. Create `i18n/<code>/common.json` + one file per page.
2. Add `<code>` to `LANGS` in `build.mjs`.
3. Extend the language-selection logic in `templates/partials/head.html` **and** `assets/js/motify.js` (both currently branch `he` vs `en`).
4. RTL is automatic — see below.

## Runtime language selection

The `<head>` bootstrap (`templates/partials/head.html`) picks the language before first paint, in priority order:

```
?lang=  >  localStorage('motify-lang')  >  navigator.language (he* → he)  >  en
```

Then it sets `data-lang`, `lang`, `dir` on `<html>`; CSS reveals the matching `.lang-block` (default = English). If `?lang=` was present it is **saved to `localStorage` and stripped from the URL** (`history.replaceState`) so it never lingers in the address bar. The app deep-links `…/privacy.html?lang=he` to match its own language; the visitor lands on a clean URL.

The in-nav toggle (`assets/js/motify.js`, `[data-lang-to]`) flips the visible block **in place, no reload**, and persists the choice — it never writes `?lang=` to the URL.

## Scoped element IDs — `idSuffix`

Both language blocks ship in one document, so any `id` would otherwise appear twice. `build.mjs` passes `idSuffix` (`-en` / `-he`) into every language render; templates append it to IDs and their references — e.g. `#main-en`/`#main-he` (skip-link target), `nav-menu-en`, `#modes-he` (anchor links + `aria-controls`). This keeps IDs unique across the two blocks.

## RTL

Automatic. `dir` is set to `rtl` for `he` (on `<html>` by the bootstrap and on each `.lang-block` by `build.mjs`). The CSS uses logical properties throughout, so layout mirrors without per-language rules — see [design.md](design.md).
